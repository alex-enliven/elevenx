# ELDORATH IMAGE GENERATION SPEC

This directory contains the structured specification for consistent character
and art generation across the Eldorath children's fantasy book project. It is
the result of approximately 30 production generations and 9 documented
character-distinctiveness failures, with their root causes diagnosed and
encoded as machine-readable rules.

## Files in this spec

| File | Purpose |
|---|---|
| `01_characters.yaml` | Character identity sheet — absolute identifiers, no relational language. The single most important file. |
| `02_composition_and_failures.yaml` | Composition rules + taxonomy of 8 known failure modes with prevention rules and surgical regenerate templates. |
| `03_spread_template.yaml` | Schema for per-spread specs, with two filled-in examples (Spread 5 quiet, Spread 16 combat). |
| `04_assembly_logic.yaml` | How to assemble prompts from the above + system architecture recommendations for Claude Code. |

## How to use this spec

### For prompt assembly

1. Define a per-spread spec following the schema in `03_spread_template.yaml`.
2. The prompt assembler walks `04_assembly_logic.yaml` block order (1-15).
3. For each block, it pulls content from the spread spec or static rules.
4. For cast blocks, it injects FULL canon descriptions from `01_characters.yaml`.
5. For high-risk characters (Damian, Alex), it injects the character's
   `stability_note` and anti-pattern reminders.
6. For multi-character action scenes (4+ characters in cast), it injects the
   visual distinctiveness rule.
7. The assembled prompt goes through a pre-check pass that scans for known
   anti-patterns (relational descriptors for Damian, "shield-blade hybrid"
   for Alex, missing Fynn absence directive for spreads 9-27).

### For regenerate prompts

When a generation fails:

1. Classify the failure using the `failure_modes` taxonomy in
   `02_composition_and_failures.yaml`.
2. Use the `surgical_regenerate_template` for that failure mode.
3. Always restate the four format invariants verbatim (see `format_invariants`
   in document 02).
4. Always specify what to KEEP from the previous generation.
5. Inject character lockdown for any character involved in the failure.

### For acceptance gating

Some checks are automatable (aspect ratio, OCR for text). Most require human
review (character distinctiveness, scale appropriateness, moment-vs-portrait
test). The 16-point checklist is in `04_assembly_logic.yaml` under
`v6_16_point_checklist`.

## Key principles to internalize

1. **Absolute identifiers, never relational.** "Damian has warm honey-blond
   hair" works. "Damian has hair between Lionn's and Zaya's" fails ~50% of
   the time in multi-character action scenes.

2. **Format invariants are restated in every prompt and every regenerate.**
   Conversation memory is unreliable for hard format constraints. The four
   invariants (A4 portrait, 6% blend zone, 8% clear, focal at 60-70%) appear
   verbatim every time, no exceptions.

3. **Damian and Alex are the production bottlenecks.** Six of nine documented
   failures involve Damian collapsing toward Lionn. Three involve Alex losing
   scale or weapon identity. The character identity sheet's stability_notes
   for these two are the most important content in the whole spec.

4. **THE MOMENT block is the longest block in every prompt.** When CHARACTERS
   PRESENT is longer than SCENE ACTION, the model produces hero shots. When
   THE MOMENT is the dominant block, the model produces moments.

5. **Reference image attachment is the API substitute for conversation
   continuity.** Every API call attaches the hero lineup; villain-present
   scenes attach the villain sheet; in-chapter spreads attach the most
   recent approved spread.

6. **Parchment is composed in HTML, never generated by AI.** The parchment
   template is a locked asset. Including parchment in AI generation causes
   waste and inconsistency.

## What this spec does NOT cover

- Spread 1 (the world map) — generated as a unique full-spread exception,
  outside this system's scope.
- HTML post-production composition — separate pipeline; parchment + text
  overlay + page numbers + spine shadow.
- Cover artwork (front/spine/back) — separate generation flow with its own
  reference set.
- The Dutch markdown overlay text — already drafted per spread; not the
  responsibility of the prompt assembler.

## Production data included

`04_assembly_logic.yaml` contains a `production_failure_log` section
documenting all 9 known character-distinctiveness failures from the original
ChatGPT production. These can serve as test cases for the regenerate
generator: given the failure description, does the system produce a
regenerate prompt similar to the one that fixed the issue?

## Implementation order recommended

1. Build the prompt assembler as a pure function.
2. Test on Spread 5 (quiet) and Spread 16 (combat) example specs.
3. Verify output matches the prompts that produced approved generations
   in production.
4. Add the failure-mode pre-check.
5. Add the regenerate generator using the failure log as test cases.
6. Add the API caller and reference image attacher.
7. Add the automated acceptance checks (aspect ratio, OCR).
8. Wire to a UI for human review and approval.
